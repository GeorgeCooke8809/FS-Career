# Code Structure

How the repo is laid out and how the pieces fit together. For the *design* (what the app is trying to be), see [`OVERVIEW.md`](OVERVIEW.md). For table-level detail, see [`DATA_DICTIONARY.md`](DATA_DICTIONARY.md) and [`ERD.md`](ERD.md).

## Top-level layout

```
run.py               # entry point for the shipped app (currently a stub)
run_admin.py          # entry point for the internal DB admin GUI
pyproject.toml        # deps, managed via uv
alembic.ini            # alembic config (points at migrations/)

models/                # SQLAlchemy ORM models — the shared data layer
migrations/             # Alembic migration scripts (schema history)
data/                  # the SQLite DB itself, seed data, and seed/build scripts
scheduling/             # gameplay logic that queries the data layer (route/schedule generation)
ui/                    # the shipped app's GUI (CustomTkinter) — not started beyond a stub
.devtools/db_admin/     # internal-only Tkinter GUI for browsing/editing seed data
.docs/                 # this documentation
```

Everything reads/writes the single SQLite file at `data/fs_career.db` through the models in `models/` — there is no other persistence path.

## `models/` — data layer

Plain SQLAlchemy `DeclarativeBase` models, one file per table: `airport.py`, `airline.py`, `aircraft_family.py`, `aircraft.py`, `route.py`. `models/__init__.py` re-exports all of them plus `Base`.

`models/base.py` owns the engine/session machinery:
- `REPO_ROOT`, `DB_PATH` — resolves `data/fs_career.db` relative to the repo root regardless of cwd.
- `engine` — the module-level SQLAlchemy engine, with a `connect` event listener that turns on `PRAGMA foreign_keys=ON` (SQLite doesn't enforce FKs by default).
- `Session` — a `sessionmaker` bound to `engine`.
- `with_session` — decorator that opens a session, passes it as the first arg to the wrapped function, commits on success, rolls back and re-raises on exception, always closes. Use this for one-off scripts/functions rather than managing a session by hand.

`.devtools/db_admin/db.py` defines its own `SessionLocal`/`get_session()` against the same `engine` (with `expire_on_commit=False`, since the GUI keeps objects around across redraws) — it does not reuse `with_session`, since the GUI holds one long-lived session for the app's lifetime rather than one per call.

Schema details (columns, keys, constraints, design rationale) live in `DATA_DICTIONARY.md`, not here — don't duplicate them.

## `migrations/` — Alembic

Standard Alembic layout (`env.py`, `script.py.mako`, `versions/`). Run `uv run alembic upgrade head` to apply. One migration per schema change; filenames are Alembic's autogenerated `<rev>_<slug>.py`. When changing a model in `models/`, generate a matching migration rather than hand-editing `fs_career.db`.

## `data/` — the dataset

- `fs_career.db` — the actual SQLite database (checked in, since it's the bundled reference dataset the app ships with).
- `logos/{icao}.png` — airline logo files, referenced by `airlines.has_logo` rather than stored as DB blobs.
- `seed/` — one `build_<table>_seed.py` + `seed_<table>.py` pair per table:
  - `build_*_seed.py` fetches/transforms source data (Wikipedia, OpenFlights, OurAirports, ICAO 8643) into a `<table>_seed.json` file in this folder. These are one-shot/rerunnable-but-slow scripts (web scraping, geocoding) — not part of the app's runtime path.
  - `seed_*.py` reads the corresponding `*_seed.json` and inserts/upserts into `fs_career.db` via the models. This is the fast, repeatable half — safe to rerun against a fresh DB.
  - `raw/` — unprocessed source downloads the `build_*` scripts consume.
  - Anything not fitting that pair (e.g. `fetch_airline_logos.py`, conflict-resolution CSVs) is a one-off tool used during that table's import; see the relevant `memory/project_*.md` note for why it exists.

## `scheduling/` — gameplay logic

Where game logic that operates on the data layer lives, as opposed to raw data access (`models/`) or data curation (`data/seed/`). Expect this package to grow as the roadmap's route-generation/hiring/career-progression items (see `OVERVIEW.md`) get built. Currently:

- `random_route.py` — `get_random_route(airline_icao, origin, max_duration, min_duration)`: picks a random `Route` for an airline from a given origin within a duration band.
- `route_between_points.py` — `get_route_between_points(airline_icao, origin, destination)`: looks up the specific route connecting two airports for an airline (used to find the return/connecting leg after picking a random outbound one).
- `create_schedule.py` — `create_schedule(airline_icao, origin, no_flights, min_flight_duration, max_flight_duration)`: builds a multi-leg pilot schedule, branching on `Airline.network_model`:
  - `hub_and_spoke` (`create_hub_and_spoke_schedule`) — alternates a random outbound leg from `origin` with the known return leg back to `origin`, bounded by a 600-minute (10-hour) duty-time cap. An odd `no_flights` is allowed to end away from base (a layover) rather than forcing an even number of legs.
  - `point_to_point` (`create_point_to_point_schedule`) — chains random legs from wherever the previous leg landed, then retries (up to 10 times) to find a route back to `origin` for the final leg; if that fails, or the whole schedule exceeds the duty-time cap, it recurses with one fewer `attempts_remaining` and restarts from scratch. Not graph-pathfinding — a real shortest-path/reachability solve is a possible future improvement (see comment in the file) but the retry approach has been sufficient so far.
  - `no_flights == 1` short-circuits to a single `get_random_route` call regardless of network model.
  - Two known gaps flagged by `TODO`s in the file: no type-rating constraint yet (routes can be generated for any aircraft), and no logic to redirect an out-of-position schedule back to the player's actual base once career mode exists.

All three modules are re-exported from `scheduling/__init__.py`.

## `ui/` — shipped app GUI

CustomTkinter-based GUI for the actual player-facing app. Currently just an import stub in `__init__.py` — not started. When built, expect it to follow the same GUI/business-logic split as `.devtools/db_admin` (screens own layout, a separate module owns queries) rather than mixing DB calls into widget code.

## `.devtools/db_admin/` — internal DB admin GUI

Not part of the shipped app — a development-only tool for browsing/editing the seed tables directly, launched via `run_admin.py`. Structure:

```
app.py       # App(ctk.CTk) — builds the tabview, one tab per table, owns the single session
db.py         # SessionLocal/get_session() — see models/base.py note above
repo.py       # all querying/CRUD, grouped by table — the only module that imports sqlalchemy.select directly
screens/      # one screen per table tab, each a BaseTableScreen subclass
forms/        # one Add/Edit dialog per table, each a BaseRecordForm subclass
widgets/      # small reusable CTk widgets (RecordTable, Pager, confirm/error dialogs, searchable combobox, image thumbnail)
```

**Layering**: `screens/*` and `forms/*` never call SQLAlchemy directly — they call into `repo.py`, which is the only place queries/CRUD are written. This keeps the GUI code free of query logic and keeps `repo.py` a flat, greppable list of what operations exist per table.

- **`repo.py`** — per table: `search_<table>(session, text, ...filters, page, page_size) -> (rows, total_count)` for paginated search/filter, plus `create_/update_/delete_<table>`. Create/update/delete let `IntegrityError` propagate — the screen/form layer is the boundary that turns that into a user-facing message (via `widgets/error_dialog.friendly_message`). A few `count_routes_for_*`/`count_aircraft_for_family` helpers exist to give a friendlier pre-delete warning (e.g. "12 routes reference this airline") before the FK constraint would reject the delete.

- **`screens/base_screen.py`** (`BaseTableScreen`) — shared skeleton: search box (debounced), a filter area, a paged `RecordTable`, an "+ Add" button. Subclasses (`AirlinesScreen`, `AirportsScreen`, `AircraftFamiliesScreen`, `AircraftScreen`, `RoutesScreen`) only implement the per-table hooks: `fetch_rows`, `format_row`, `cell_widgets`, `build_filters`, `open_add_form`/`open_edit_form`, `do_delete`, `record_label`. Add a new table's screen by subclassing this rather than rebuilding the search/page/table wiring.

- **`forms/base_form.py`** (`BaseRecordForm`) — shared Add/Edit dialog skeleton (`ctk.CTkToplevel`). One instance handles both modes: `record=None` is Add, `record=<instance>` is Edit. Subclasses implement `build_fields`, optionally `populate`/`validate`, and `save` (which calls the matching `repo.py` create/update). Wires Save/Cancel and turns `IntegrityError` on save into a dialog via the same `error_dialog` helper.

- **`widgets/`** — `RecordTable` (the data grid, supports per-column custom cell widgets via `cell_widget_factories`, e.g. `image_thumbnail` for logos), `Pager`, `confirm_dialog`/`error_dialog` (the latter's `friendly_message` turns raw `IntegrityError` text into something like "Can't delete — referenced by N routes"), `searchable_combobox` (used for FK pickers in forms, e.g. picking an airline/airport/family by search-as-you-type).

To add a new table to the admin tool: add the model, an Alembic migration, a `repo.py` section, a `screens/<table>_screen.py`, a `forms/<table>_form.py`, register the tab in `app.py`'s `TABS` list.

## Running things

- `uv run run.py` — shipped app (currently a stub).
- `uv run run_admin.py` — DB admin GUI. It adds `.devtools` to `sys.path` by filesystem path (since a leading dot isn't a valid Python package segment) rather than using `-m` dotted-module resolution.
- `uv run alembic upgrade head` — apply migrations to `data/fs_career.db`.
